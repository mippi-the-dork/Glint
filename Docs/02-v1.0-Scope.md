# 02 — v1.0 Scope and Acceptance

[← Index](README.md) · [21 — Automatic Vision](21-Automatic-Lens-Vision-and-Workflows.md) · [28 — Release Gates](28-Automatic-Mode-Testing-and-Release-Gates.md)

> **Scope revision:** Automatic HDR camera lens response **is required** for v1.0. The earlier “automatic bright-pixel discovery beyond v1.0” statement is withdrawn.

## Required platform

- UE5.8.0–5.8.3 (verify each) / Win64 desktop deferred / packaged runtime and editor.
- Validate, but do not promise without proof: forward, other RHIs, scene capture, split-screen, Movie Render Queue.
- Not required by default: mobile, console, VR/stereo, path tracing, support for engine forks.

## Required v1 features

| Area | Acceptance |
|---|---|
| **Lens Asset** | Dedicated **Glint Lens** Content Browser asset, presets, project default, camera-specific optional override and normal save/cook behavior |
| **Flare Asset** | Dedicated **Glint Flare** Content Browser asset (legacy planning `UGlintAsset`) with art-directed elements, presets and reusable templates |
| **Automatic image response** | A camera without manually added Glint sources generates ghost/streak/glow effects from qualifying **HDR emissive/specular image regions** |
| **Automatic candidates** | GPU highlight extraction and bounded top-K source descriptors can drive at least representative full Glint element compositions; no CPU readback, unlimited sources or per-candidate Actor creation |
| **Lens controls** | Sensitivity, intensity, max prominent candidates, source area/contrast handling, major ghost/streak style, lens dirt and separate quality controls |
| **Automatic diagnostics** | Threshold/luminance preview, accepted/rejected candidates, rankings, source suppression, active cost tier and render stages |
| **Source modes** | Automatic, Authored, Hybrid; source conflicts have explicit dedup/priority policies |
| **Editor** | Native Slate dockable lens and flare experiences, real-time preview, element stack, Details, relevant property gating, tooltips and undo/redo |
| **Elements** | Twelve Optical Flares-inspired families plus Texture Sprite from previous spec, with familiar appearance/transform/trigger controls |
| **Optical response** | Shared lens profile, ghost axis mapping, color/aberration, aperture/iris shape inheritance, authored local overrides, basic CineCamera focal/filmback policy |
| **HDR compositing** | GPU-rendered independent image field and instanced elements, well-defined pre-exposure and tone-map behavior, source-independent camera-space dirt |
| **World sources** | Optional point/directional source components and actor-free temporary Blueprint/C++ source API |
| **Occlusion** | Depth-aware visibility for authored opaque/masked world sources; automatic source visibility uses detected scene image, not fabricated world depth |
| **Dynamics** | Shared Dynamic Triggering, deterministic time/flicker, camera cuts, temporal hysteresis, auto source candidate persistence |
| **Presets** | Original lens styles plus full flare and individual element presets |
| **Scalability** | Off/Low/Medium/High controlling field resolution, candidate cap, element LOD, texture details and compositing cost |
| **Diagnostics/perf** | GPU stage markers for detection/field/candidates/instances/dirt/composite and native debug overlays |
| **Packaging/tests** | UE native `Automation RunTests Glint`, deterministic images, packaged Win64 tested with no engine modifications |
| **Documentation** | User guide, design/technical spec, automatic behavior, limits, gameplay integration, verified performance table |

## Acceptance gates

1. Assign one Glint Lens as Project Default → automatic lens flares work in packaged game on HDR bright sources **without additional Actors**.
2. Camera Sensitivity adjusts which spots qualify; Intensity adjusts output strength separately; limits are honored and visibly explained.
3. Both cheap image-space flares and richer automatically selected element compositions function under a bounded GPU budget; if the richer method proves too costly, **re-evaluate v1 scope or optimization**, do not silently ship a limited system while claiming complete parity.
4. Authored source integration works without ghost double-counting by default and with deliberate override controls.
5. A skilled artist can edit all planned elements in native Glint Flare editor with predictable transforms and dynamic triggers.
6. Camera exposure, cuts and resolution do not cause critical ghost history/sensitivity artifacts.
7. Native tests pass, cooked assets load, editor/PIE/packaged demo behave consistently, reference machine actual GPU timings recorded.

## Deferred beyond v1

- Physically tracing full lens glass per camera or generating exact manufacturer prescriptions in realtime.
- Unrestricted generation of hundreds of independently high-detail flare templates: **bounded candidates** are required instead.
- Automatic understanding of lights offscreen or with no bright visible scene pixels; use authored sources where needed.
- Full transparency/fog/cloud/path-tracer parity, unless independently proven.
- Import of proprietary Optical Flares/Maxon/other plugins' assets or commercial lens data.
- Universal platforms/renderer compatibility, large-scale network replication, automatic image-to-flare reference reconstruction.

## Provisional performance philosophy

The earlier `≤0.6ms for eight authored sources` goal only describes an **authored-only scenario** and is not a whole automatic render budget. No numeric **total** auto mode GPU target should be represented as achieved or final until a measured reference hardware and complete detection+field+candidate+composite pass exist. See [07](07-Performance-and-Scalability.md) and [28](28-Automatic-Mode-Testing-and-Release-Gates.md).

## Additional v1 runtime cost contract

The optimizer is not a post-release feature. **v1 requires** mixed-resolution routing for soft vs sharp details, global/per-view candidate limits, GPU-only candidate transfer, shared camera dirt and source analysis, basic instancing by element family, an always-safe disabled path, source LOD fade/hysteresis, and stage-level GPU diagnostics. Lens elements must not become individual runtime Actors or dynamic material instances.

**Not required for v1:** polynomial physical optics reconstruction, tiled ghost accumulation, unconditional reuse of UE's Bloom targets, async compute, or autonomous target-ms adaptive quality. Those remain measurable research paths, not launch dependencies. See [32](32-Perceptual-Optimization-and-Render-Budget.md).

## Cross-engine refinement (see [37](37-Cross-Engine-Findings-and-Prototype-Gates.md))

- Generic **Repeater** authoring (uniform/curve/deterministic random) and safe nesting are part of the native editor's v1 element workflow; they compile into compact runtime instances. This is not a requirement for a separate runtime per-sub-element Actor.
- Include basic screen-edge deformation and explicit visibility-response modes (uniform as shipped baseline; optional shape-reactive path only if E5 proves worthwhile).
- Include a **stock Unreal lens flare coexistence** warning/setup policy and per-camera contribution clamp to avoid accidental double effects.
- Automatic source analysis must preserve strong subpixel/small highlights, not only area-averaged luminance, and must avoid merging distinct neighboring headlights without an intentional tradeoff.
- Lens Profile's stylistic intent (Clean/Cinematic/Anamorphic/Sci-Fi/Visor) should be understandable without physical optics expertise. Original presets only.
